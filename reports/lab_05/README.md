# Лабораторная работа №5: Параллельная генерация фрактала Мандельброта (Stanford CS149)
---
## 1. Цель работы

Реализовать параллельную версию генерации фрактала Мандельброта с использованием многопоточности C++ (std::thread). Провести анализ производительности, выявить проблему дисбаланса нагрузки и оптимизировать распределение работы между потоками. Работа выполнена в рамках задания Stanford CS149 Assignment 1, Program 1.

## 2. Описание задачи

Множество Мандельброта — это фрактал, определяемый в комплексной плоскости. Для каждого пикселя изображения вычисляется количество итераций комплексного отображения z(n+1) = z(n)^2 + c до выхода за границу круга радиуса 2. Вычислительная сложность разных пикселей сильно различается: пиксели внутри множества требуют максимального числа итераций, а пиксели вне множества — всего нескольких.

Исходный код предоставлен в репозитории Stanford CS149. Последовательная версия реализована в функции `mandelbrotSerial()`.

## 3. Модификация программы

### 3.1. Базовая многопоточная версия
Для распараллеливания использован механизм `std::thread` из C++14. Изображение разбивается на полосы строк, каждая из которых обрабатывается отдельным потоком. Каждый поток получает свою структуру `WorkerArgs` с параметрами задачи и номером потока.

### 3.2. Оптимизация: чередующееся распределение строк
Для устранения дисбаланса нагрузки применено **чередующееся распределение строк (interleaved row assignment)**:

    for (int y = args->threadId; y < (int)args->height; y += args->numThreads) {
        for (int x = 0; x < (int)args->width; ++x) {
            float px = args->x0 + x * dx;
            float py = args->y0 + y * dy;
            args->output[y * (int)args->width + x] = mandel(px, py, args->maxIterations);
        }
    }

Вместо непрерывных блоков строк каждый поток обрабатывает строки с шагом `numThreads`. Это гарантирует, что каждый поток получит статистически одинаковое количество «сложных» и «простых» пикселей.

## 4. Методика эксперимента

- **Разрешение изображения:** 1600×1200 пикселей
- **Максимальное число итераций:** 256
- **Конфигурации потоков:** 1, 2, 4, 8, 16
- **Виды фрактала:** View 1 (общий вид) и View 2 (фрагмент границы)
- **Метрика:** Ускорение (Speedup) = T(1 поток) / T(N потоков)

## 6. Анализ результатов

### 6.1. Дисбаланс нагрузки
При наивном разбиении изображения на непрерывные блоки строк (top/bottom) для View 2 наблюдался сильный дисбаланс нагрузки: одни потоки завершались за 20-30 мс, в то время как другие работали 100+ мс, простаивая в ожидании `join()`. После внедрения замеров времени стало очевидно, что общее время выполнения определяется самым медленным потоком.

### 6.2. Эффективность оптимизации
Применение чередующегося распределения строк выровняло время выполнения всех потоков (разница менее 5%). Для View 1 ускорение составило 4.94x на 8 потоках, для View 2 — 4.50x.

### 6.3. Причины нелинейного ускорения
Наблюдаемое ускорение ~5x для 8 потоков вместо теоретических 8x объясняется двумя факторами:
1. **Накладные расходы:** Создание и уничтожение потоков, а также переключение контекста.
2. **Деградация кэш-локальности:** Чередующееся распределение заставляет разные потоки обращаться к разным, далеко отстоящим друг от друга строкам памяти, что увеличивает количество промахов кэша (cache misses) по сравнению с последовательным доступом.

### 6.4. Ограничения масштабирования (16 потоков)
При запуске с 16 потоками ускорение составило ~6.1x, что лишь незначительно выше результата для 8 потоков (~4.9x). Тестовая система оснащена процессором с 4 физическими ядрами и технологией Hyper-Threading (8 логических потоков). При запуске 16 потоков операционная система вынуждена делить ресурсы 8 логических ядер между 16 программными потоками, что вызывает дополнительные накладные расходы на переключение контекста и конкуренцию за общие ресурсы ядра.
