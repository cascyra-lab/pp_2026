## 2. Модификация программы
К последовательной версии из ЛР №1 добавлена директива OpenMP:

```cpp
#pragma omp parallel for schedule(static)
for (int i = 0; i < N; ++i) {
    for (int k = 0; k < N; ++k) {
        double a_ik = A[i * N + k];
        for (int j = 0; j < N; ++j) {
            C[i * N + j] += a_ik * B[k * N + j];
        }
    }
}
```


Параллелизация выполнена по внешнему циклу `i`, так как итерации независимы. Используется статическое распределение итераций (`schedule(static)`), что оптимально для равномерной нагрузки.

## 3. Методика эксперимента

- **Размеры матриц:** N = 200, 400, 800, 1200, 1600, 2000
- **Число потоков:** p = 1, 2, 4, 8
- **Метрики:**
  - Ускорение: $S_p = T_1 / T_p$
  - Эффективность: $E_p = S_p / p$

## 5. Анализ результатов

### 5.1. Влияние размера задачи на ускорение

При малых размерах матриц (N=200, 400) наблюдается **суперлинейное ускорение** на 2 потоках ($S_2 > 2$). Это объясняется тем, что данные помещаются в кэш L3 процессора, и два ядра эффективнее используют кэш-память, чем одно. При N=200 и p=8 время выполнения возросло по сравнению с p=4 из-за накладных расходов на создание потоков и синхронизацию OpenMP.

### 5.2. Memory-bound характер задачи

Для больших матриц (N ≥ 800) ускорение растёт монотонно, но эффективность падает с увеличением числа потоков. Это классическое поведение **memory-bound** задач: узким местом становится пропускная способность оперативной памяти, а не вычислительная мощность ядер.

### 5.3. Масштабируемость

С ростом размера задачи ускорение при фиксированном числе потоков увеличивается. Это подтверждает закон Амдала: чем больше вычислительная часть задачи, тем лучше масштабируемость.

## 6. Выводы

1. Параллельная версия с OpenMP демонстрирует ускорение на всех размерах матриц.
2. Для малых задач (N ≤ 400) оптимальное число потоков — 2-4, дальнейшее увеличение потоков снижает производительность.
3. Для больших задач (N ≥ 800) ускорение растёт с числом потоков, но эффективность падает из-за ограничений пропускной способности памяти.
4. Оптимизация порядка циклов `i-k-j` из ЛР №1 критически важна для производительности — без неё параллельная версия работала бы значительно медленнее из-за промахов кэша.
